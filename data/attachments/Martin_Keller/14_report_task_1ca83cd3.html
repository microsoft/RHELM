Discussion Summary

1. System and Circuit Diagrams – Feedback by Julia Schneider

Julia began by reviewing the latest system and circuit diagrams. Although the formal version of the diagram was not referenced during the meeting, Julia highlighted the necessity of clearly versioned documentation. She noted specific inconsistencies in power rail labeling between the system overview and the detailed schematic, warning of potential confusion during maintenance and assembly if left unaddressed.

Additionally, Julia pointed out signal integrity concerns at the analog-to-digital interface points. She recommended a thorough review to ensure compliance with IEC 60601-1 requirements on electromagnetic compatibility. She emphasized the importance of maintaining separate ground planes and adequate shielding, both considered best practices in embedded systems design.

Julia also requested the addition of test points on the microcontroller-side interfaces. Such test points will make in-circuit debugging more efficient and reinforce design for testability. The group agreed that DFT improvements will reduce troubleshooting time and support future manufacturing test efforts.

An incomplete component legend in the schematic was also flagged. Julia asked for an updated and comprehensive legend to be added to the documentation. Ensuring all files—including design diagrams, schematics, and supporting documentation—are tracked in a version-controlled, shared repository remains a key priority. Regular, recorded updates will prevent version drift and ensure all team members are working from the latest specifications.

Action Follow-ups:
- Identify and apply explicit versioning to all system and circuit diagrams
- Complete and distribute the updated component legend
- Add microcontroller-side test points as suggested

2. Firmware Bug Report – Presented by Mehmet Yilmaz

Mehmet presented recent findings from firmware testing. The most critical issue observed has been the intermittent failures in the sensor polling routine, which tend to appear after several hours of system operation. While the precise logs were not available at this meeting, Mehmet committed to supplying detailed logs and trace files by 2024-02-05 for further analysis. The team discussed potential causes, with suspicion falling on timing irregularities or resource conflicts after extended uptime.

Mehmet further described recurring SPI bus timeout errors at elevated ambient temperatures, specifically above 50°C. He hypothesized that these could be the result of protocol misalignment, possibly due to timing deviations exacerbated by hardware performance changes in high-heat conditions. To support this analysis, additional hardware-in-the-loop testing will be conducted.

A possible memory leak within the Interrupt Service Routine (ISR) was also referenced. This issue was first indicated by results from automated static analysis, which flagged resource mismanagement patterns. Although specific error codes were not detailed during the meeting, Mehmet will consolidate findings and provide a full static analysis report and tickets via JIRA (project SensorQA). The team agreed to strengthen the integration of continuous static analysis into the CI workflow going forward.

Key Points:
- All issues are actively tracked in the SensorQA JIRA project
- Logs and full bug trace data to be provided for collaborative troubleshooting
- Emphasis placed on improving defect traceability and ensuring robust continuous integration practices

3. Developer Commitments and Patch Planning – Reported by Martin Keller

Martin outlined his commitments in response to the QA findings and feedback. He will revise the sensor polling logic, focusing extra attention on robust exception handling and edge-case management to prevent further intermittent failures.

To address SPI bus timeouts, Martin will recalibrate the peripheral's configuration, aligning timing parameters with revised requirements established through high-temperature testing. He noted that updated results from HIL testing will inform final adjustments.

Furthermore, Martin will initiate a static code analysis process in line with MISRA C compliance guidelines. This integration will be part of the pre-patch pipeline, planned to commence by 2024-02-06. Martin confirmed all code changes will undergo a thorough peer review and regression test cycle.

The team referred to the Sensor QA Test Plan (version 2.5) as the framework for validation, but Martin and the QA lead agreed to verify the test plan’s latest version and update as needed. Martin reiterated his commitment to rigorous unit testing, peer reviews, traceability of all code changes, and a consistent, incremental delivery approach to enable ongoing QA validation.

Action Follow-ups:
- Initiate and document updates to the polling routine and SPI configuration
- Complete static analysis onboarding for all firmware changes
- Ensure regression tests and code reviews are linked to each commit via feature and bug-fix traceability

Next Steps and Quality Assurance Improvements

The team agreed on several steps to improve both the technical and procedural aspects of the project’s QA process:

  • Finalize Root Cause Analyses:
    Mehmet and Martin will complete the review of incident and trace logs for firmware issues by 2024-02-05, ensuring all critical failures are comprehensively analyzed and properly documented.

  • Implement and Validate Corrective Fixes:
    Martin is responsible for delivering code patches as committed, integrating static analysis tools, and running peer reviews for all significant changes. All updates will be regression-tested per the updated Sensor QA Test Plan.

  • Expand Regression Test Coverage:
    The QA team will prepare and rollout extended test cases that specifically address high temperature operation, SPI bus faults, and ISR memory management issues. Comprehensive validation scripts will be released to support these tests.

  • Enhance Documentation and Version Control:
    Julia will formalize procedures for schematic and documentation updates, ensuring all technical files are version-controlled and readily accessible to the team by 2024-02-07.

  • Audit Quality Assurance Practices:
    The team will review compliance with current QA protocols, including code peer reviews, adherence to static analysis, and test-driven development (TDD). The QA Lead will prepare a checklist for the next session to further align workflows with recognized industry standards.

The next QA review meeting has been scheduled for 2024-02-16. The agenda will focus on progress tracking, validation of pending fixes, and discussion of process improvements.
